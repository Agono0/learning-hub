# S3-24 — Boards page: Kanban + Eisenhower built-ins + custom rule views

## Core — `packages/core/src/boards.ts` (new, exported from the index)

The board engine as pure functions over the SP task model:

- **Rule chips** — `boardRuleChipSchema = { id, label, filter, apply }`.
  Filter keys: `isDone, wonthado, priority[], projectId, tagId, hasDue,
  overdue, dueWithinDays`; apply keys: `isDone, priority, projectId,
  add/removeTagId, clearDue | dueInDays | due` (a zod refine keeps
  `clearDue` + a due out of the same chip).
- **Built-in Kanban** (`kanbanBoardView()`): Backlog/Low/Medium/High + Done
  columns; a drag re-prioritizes or completes.
- **Built-in Eisenhower** (`eisenhowerBoardView()`): urgency is DATA —
  overdue, or due/deadline within `URGENT_WINDOW_DAYS` (7) — importance is
  `high|medium` priority. Q1 do-now (high + due in a week), Q2 schedule
  (high + no due), Q3 quick wins (low + due), Q4 someday (low + no due).
  `eisenhowerQuadrant(task, today)` exported for S3-84's keyboard nav.
- **`buildBoard(view, tasks, today)`** — first matching column wins (a task
  appears exactly once); tasks no column claims come back in `unmatched`
  so the page can be honest instead of hiding work.
- **`applyChip(task, chip, today)`** — the drag contract: immutable patch,
  re-validated through `taskItemSchema`; completing stamps `doneAt` from
  last-known state (the PATCH handler re-stamps server-side); a won't-do
  decision is never silently cleared by a re-open; impossible patches throw
  at the boundary. Timestamps are NOT fabricated (pure module — no clock).
- `addDays(today, n)` — UTC day-key math, month/year safe.

## Page — `apps/web/app/boards/page.tsx`

Tabs (Kanban / Eisenhower / Custom). Tasks from
`GET /api/tasks?includeDone=1&includeWontdo=1&limit=500` (react-query); a
drop applies the column's chip via `applyChip` then PATCHes
`/api/tasks/[id]` with `{ priority, isDone, due, deadline }` and updates the
query cache optimistically. Touch fallback: every column carries a
"Move a task here…" select (44px) because HTML5 drag is unreliable on touch
(S3-82/S3-84 refine interactions; S3-100 owns the a11y sweep). The
"Unmatched" dashed column shows tasks no rule claims. Custom-view builder:
preset chips → ordered columns → named view. SSR-safe: `today` and data are
client-only (effect-only reads), so `renderToString` matches hydration.

## Custom views persistence — `apps/web/src/lib/board-views.ts`

Device-local (`lh-board-views`, zod via the core `boardViewSchema` with
`kind: 'custom'`). Why not the S3-17 `task_views` rows: those persist a
single filter per view — enough for filtered lists, not for multi-column
boards with per-column chips. When parity wants synced boards, that is a
schema batch (LEAD, docs/SHARED_CHANGES.md), not worker work.
