## Behavior notes

- **Start (POST)** — accepts the core start schema extended with
  `tier?: 'owner' | 'accessibility' | 'windows-admin' | 'windows-basic'`;
  the repo stamps `state: 'locked'`, `hardCapAt` (start + 4h) and `tier`
  (M2-03). Duplicate-session conflicts → 409, validation → 400.
- **Status (GET)** — the lock payload now carries the persisted M2-03 columns
  (`state` / `tier` / `hardCapAt`) for the UI + report card.
- **Extend (POST)** — planned end += `extraMinutes`, clamped to the hard cap;
  409 while an early exit is pending or no session is running.
- **Exit (POST)** —
  - `request` → 60s cooldown (unchanged);
  - `confirm` now REQUIRES `pin` + `vault` (missing → 400). The vault record
    is device-local (created client-side via core `createPinVault`); the
    handler verifies with core `verifyPin` (PBKDF2, constant-time). Wrong PIN
    → 401; cooldown active (even with a correct PIN) → 409; success ends the
    session (`state: 'ended'`, `exitReason: 'pin'`) and appends the friction
    event;
  - **Rate limit:** 5 failed PIN attempts per session inside a rolling 5-min
    window → 429 + `retry-after` (in-memory per process; pin.ts names the
    handler as the rate-limit owner);
  - `cancel` → resistance-win friction event (unchanged).
- **History (GET)** — recent max sessions (`listMaxFocusSessions`) + exit
  reflections (`listMaxFocusExits`) for the M2-25 UI.

## PIN vault storage decision

The vault stays **device-local** (webview localStorage, client-created), so
no `user_settings` column is needed for M2-04. If the lead later wants the
vault server-side (cross-device), that is a shared-file request — see
docs/SHARED_CHANGES.md pattern.
