# M2-21 — Settings locked during a Max Focus session

**Status:** done. **Branch:** `feature/mega-run`. **Worker:** W2.

## Server (enforcement)

`apps/web/src/server/handlers/settings/route.ts` — the settings `PUT` now
checks `getActiveFocusLock()` before applying anything: an ACTIVE Max-mode
lock throws `ApiError(423, 'Settings are locked while a Max Focus session is
running. Exit the session to change settings.')`. GET stays readable (the UI
renders state from it), and **standard focus sessions do not lock settings**
— only the Max commitment device does. 423 Locked is the semantically exact
status.

## Client (mirror, not enforcement)

`apps/web/app/settings/page.tsx` — a `['focus-max-lock']` query (10s
refetch) drives:

- a warning `Callout` above the save row: "Settings are locked during Max
  Focus…";
- the global `Save settings` button renders `disabled` while
  `lock.active && lock.mode === 'max'`.

Other save paths that bypass the button (theme preset clicks, learner-profile
apply) still hit the server and surface the 423 message through their
existing error toasts — the server is the single enforcement point, the UI is
just honest about it.

## Tests

`apps/web/tests/max-focus-settings-guard.test.ts` (settings-haptics pattern,
temp DB):
1. PUT works with no session (200);
2. a STANDARD focus session does not lock settings (200);
3. with a Max session active: PUT → 423 with the locked message, GET → 200
   and the write verifiably did NOT land;
4. ending the session via the M2-03 `endMaxFocusSessionByReason` setter
   (battery) lifts the guard — PUT succeeds and persists.
