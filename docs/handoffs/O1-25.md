# O1-25 — Update check interval + Wi-Fi-only honored by the check scheduler

## Where it landed (and why not update.rs)

The task row named `update.rs` ("Rust scheduler"), but the settings the
scheduler must honor (`autoCheckIntervalHours`, `wifiOnly`) are **device-local
webview state** (`localStorage['lh-update-settings']`, O1-14). A Rust-side
autonomous loop cannot read them without a new settings bridge, and the
webview is always alive whenever the app runs — so the scheduler owns the
loop from the client service (`apps/web/src/lib/updates.ts`), and Rust keeps
the byte-heavy duties it already has (`update_download_file`, slot promote,
boot reconcile). Handoff note for the lead: if a Rust-side fallback loop is
ever wanted (webview killed mid-session), it needs a settings-sync command —
out of scope here.

## `apps/web/src/lib/updates.ts` (O1-25 section)

- `decideUpdateCheck(input)` — the pure verdict, everything injected:
  1. Play gate first (`SELF_UPDATE_ENABLED`, O1-12) — a store build never
     checks, whatever the settings say.
  2. Wi-Fi-only: defers only when the connection is **known** metered. An
     unknown state (`null`) allows the pointer check — it is a few hundred
     bytes and ask-first; hiding updates from webviews without the Network
     Information API would be worse than a tiny metered read.
  3. Interval: due when `lastCheckedAt` is missing, unparsable, or older
     than `autoCheckIntervalHours`.
- `isConnectionUnmetered()` — probe over `navigator.connection`
  (wifi/ethernet → `true`, cellular → `false`, `saveData` → `false`,
  anything else → `null` unknown). SSR-safe.
- `checkForUpdate()` — fetches the channel pointer through the existing
  `/api/update/notes` proxy (rule 1, no raw fetch), compares with
  `compareVersions` (core, nightly-tag aware), persists `lastCheckedAt`
  **only on a successful read** (a failed check does not reset the cadence).
  Dev builds (`APP_VERSION === ''`) never self-offer.
- `requestUpdateDownload(file)` — the apply path: gates play → shell →
  Wi-Fi-only (here unknown ALSO defers — this is the byte-heavy transfer the
  setting protects) → invokes the Rust `update_download_file` command
  (Tauri camelCase args). Honest result union, never throws.
- `startUpdateCheckScheduler(options)` / `stopUpdateCheckScheduler()` —
  single-instance loop: immediate tick + every `pollIntervalMs`
  (default 15 min — a *re-read* cadence, so settings changes apply without
  restart; the policy interval is the settings row). Failed ticks are
  silent and retried on cadence. `onOffer` / `onResult` callbacks are the
  glue points for the banner (O1-15) and notifications (O1-29).

## `apps/web/src/components/UpdatesSettingsSection.tsx`

"Check now" is wired: enabled when self-update is on, runs `checkForUpdate`,
and the status line states the honest outcome (latest / version available /
pointer unreachable). Replaces the old "manual checks arrive with the native
updater service" placeholder copy. SSR snapshot unchanged for the existing
test assertions.

## Tests

`apps/web/tests/update-scheduler.test.ts` (vitest, node env, mirrors the
`update-channel-flag.test.ts` style): policy matrix (due/not-due/boundary/
invalid-timestamp/metered/unknown/wifi-only-off), probe matrix (wifi,
ethernet, cellular, saveData, missing type, no navigator), check verdicts
via the mocked transport seam (up-to-date, available, dev-build never-offers,
unavailable-does-not-reset-cadence, lastCheckedAt persisted on success),
download gates + invoke shape + failure mapping, scheduler loop under fake
timers (immediate tick, cadence, stop idempotence, offer callback, metered
deferral, error resilience, play build never starts, single-instance
replacement). They run in CI — not locally (rule 17).
